## 1. System Overview

A decoupled, fully serverless architecture deployed to the **`IBD-DEV`** AWS account/profile.

```
┌──────────────┐     HTTPS      ┌───────────────┐   invoke   ┌──────────────────┐
│  Browser     │ ─────────────► │  CloudFront   │ ─────────► │  S3 (static       │
│ (Next.js SPA │                │  (CDN)        │            │  export of Next)  │
│  static)     │                └───────────────┘            └──────────────────┘
│              │
│              │   /api  HTTPS  ┌───────────────┐  proxy     ┌──────────────────┐
│              │ ─────────────► │  API Gateway  │ ─────────► │ Lambda (NestJS)  │
└──────┬───────┘                └───────────────┘            └────────┬─────────┘
       │ Cognito JWT (Authorization: Bearer)                          │ Prisma
       ▼                                                              ▼
┌──────────────┐                                              ┌──────────────────┐
│ AWS Cognito  │  (user pool, role groups)                    │  RDS MySQL       │
└──────────────┘                                              └──────────────────┘
```

- **Frontend:** Next.js (App Router, TypeScript, Tailwind) → `next build` static export → S3 → CloudFront.
- **Backend:** NestJS (TypeScript) REST API wrapped as a single Lambda handler behind API Gateway, deployed with **AWS SAM** (ADR-008). Prisma client → RDS MySQL.
- **Auth:** Cognito user pool; groups `admin`, `staff`. Unauthenticated callers are `Public`. NestJS guards validate the Cognito JWT and enforce RBAC.
- **AWS profile constraint:** all CLI/IaC/deploy actions use `--profile IBD-DEV`.

**Canonical template vs. source workbooks.** The table above is authoritative for the canonical **Actor** entity, not for the import template's accepted headers: the `.xlsx` import template (v4, `common/template-columns.ts`) is a narrower, independently-versioned set — it drops `Trader_id`, `gpsaltitude`, `gpsaccuracy`, and registration-source entirely (Trader ID is system-assigned; GPS altitude/accuracy remain DB columns but are no longer on the admin form either (D-19, 2026-10-05; superseded D-11); imports are always `TEAM_MANAGED`) and adds consent-provenance columns (Consent Method, Consent Obtained At, Consent Reference) this table does not enumerate separately. Nor is it authoritative for any particular client-supplied workbook: a source workbook with its own column spellings (e.g. `gpslatitude` variants) or sheet structure is mapped onto the import template by a per-source mapping specification before import; it is never read against this table directly. A worked example of that mapping step is produced per onboarding as the `mapping.md` of the relevant import-export spec.

```prisma
// schema.prisma (reference — authoritative shape, finalized during general-setup spec)
enum ConsentStatus {
  GRANTED
  DENIED
  UNKNOWN
}

model Actor {
  id               String   @id @default(cuid())
  traderId         String   @unique
  traderName       String
  region           String
  district         String?
  traderType       String
  sex              String?
  position         String?
  marketLocation   String?
  capacityTons     Decimal? @db.Decimal(10, 2)
  technicalSupport String?  @db.Text
  phone            String?   // PII
  email            String?   // PII
  contactPerson    String?
  otherCrops       String?  @db.VarChar(300)
  gpsLatitude      Decimal? @db.Decimal(10, 7)
  gpsLongitude     Decimal? @db.Decimal(10, 7)
  gpsAltitude      Decimal? @db.Decimal(10, 2)
  gpsAccuracy      Decimal? @db.Decimal(10, 2)
  consentStatus    ConsentStatus @default(UNKNOWN)  // public API returns GRANTED only
  crops            CropsOnActors[]
  createdAt        DateTime @default(now())
  updatedAt        DateTime @updatedAt

  @@index([region])
  @@index([traderType])
  @@index([consentStatus])
  @@index([traderName])
}

model Crop {
  id     String @id @default(cuid())
  name   String @unique   // "sorghum" | "common_bean" | "groundnut"
  actors CropsOnActors[]
}

model CropsOnActors {
  actor   Actor  @relation(fields: [actorId], references: [id], onDelete: Cascade)
  actorId String
  crop    Crop   @relation(fields: [cropId], references: [id], onDelete: Cascade)
  cropId  String
  @@id([actorId, cropId])
}
```

**Disclosure set (single source of truth, revised by `actors/public-profile-disclosure`):** consent (`consentStatus = GRANTED`) gates disclosure of every field an actor supplied, not field identity. Four constants in `src/common/pii-consent.policy.ts` carry the policy: `PUBLICLY_DISCLOSED_FIELDS` (`phone`, `email`, `sex`, `position`, `marketLocation`, `contactPerson`, `otherCrops`) — a *presence* set, required on the single-actor detail read (`GET /api/v1/actors/:id`) for a `GRANTED` actor; `CONTACT_BLOCK_FIELDS` (`phone`, `email`, `position`, `marketLocation`, `contactPerson`) — its subset, an *absence* set on the list read (`GET /api/v1/actors`), by key and by value, under every filter/page/page-size; `NEVER_PUBLIC_FIELDS` — an absence set on **every** public path regardless of consent, now including `technicalSupport` (unreviewed staff-authored free text, not an actor PII declaration) alongside `traderId`, `gpsAltitude`/`gpsAccuracy`, and the registration-provenance columns; and `PII_ALLOWLIST` — retained, **empty**, as the one-file re-restriction point should legal narrow disclosure again. Any new PII-adjacent field is classified in this module (and only there); the role-aware serializer's two projections (`toPublicListItem`, `toPublicDetail`) build public output by explicit allowlist, so the implemented set is exactly what this module declares. Exact GPS (`gpsLatitude`/`gpsLongitude`) is additionally **consent-gated**: it is surfaced only for `GRANTED` actors and withheld (`gps: null`) for non-`GRANTED`, on both list and detail.

**`ActorSequence` and the admin audit trail's duplicate-confirmation column** (`actors/consent-intake/intake-required-fields`, ADR-017). `ActorSequence { year Int @id; seq Int @default(0) }` is a per-year, race-safe counter behind the system-assigned Trader ID for admin-created and imported actors — a sibling of `RegistrationSequence` (§3.1 below), not a generalization of it, allocated via its own `INSERT … ON DUPLICATE KEY UPDATE` transaction that hands out a *range* of ids (widened from the single-increment form `RegistrationSequence` uses). The existing admin-only `ActorAuditLog` (the write history for `Actor` create/update/delete/bulk-consent/bulk-delete/import, and for registration adjudication) gained `duplicateConfirmation Json?`: a snapshot of the duplicate candidates an admin confirmed were not the same actor, carrying matched-attribute **names** only, never the matched phone/email value (NFR-3). Neither the table nor the column reaches any public projection; `pii-consent.policy.ts` is unchanged.

### 3.1 Registration & EmailVerification (public self-registration)

Two entities and three supporting counter tables behind the public self-registration intake, all distinct from `Actor` and outside the guarantees above. **`PII_ALLOWLIST` and `NEVER_PUBLIC_FIELDS` are `Actor` column lists** consumed by the `Actor` serializer — they do not, and structurally cannot, cover a table that is not `Actor`. `Registration`'s PII is instead contained **structurally**: its public surface returns at most two or three scalars and never reads the `payload` column (§8).

| Model | Purpose | PII |
|---|---|---|
| `RegistrationStatus` (enum) | `PENDING_REVIEW · AWAITING_APPLICANT · APPROVED · REJECTED · WITHDRAWN`. `AWAITING_APPLICANT` and `WITHDRAWN` are declared now but unreachable until chunk 4, so that chunk needs no enum migration; `APPROVED` and `REJECTED` become reachable with chunk 3b's adjudication (`docs/specs/admin/registration-review-queue/`). | — |
| `Registration` | One row per submission: `reference` (the applicant-facing key), `status`, `payload` (the submission, JSON, admin-only in its entirety), `submitterEmail` (the OTP-verified address — the one later published as `Actor.email` on approval), `emailVerifiedAt`, `consentAcceptedAt` (the server-witnessed instant the submission arrived — an **upper bound** on the applicant's true acceptance moment, not a client-attested one), `consentPolicyVersion`. Also declares the adjudication columns (`publishedActorId`, `reviewedBySub`/`reviewedByEmail`/`reviewedAt`, `rejectionReason`, `reviewNote`, `duplicateDismissals`) that only `docs/specs/admin/registration-review-queue/` writes, so that spec needs no migration of its own. | `payload`, `submitterEmail` |
| `EmailVerification` | The pre-verification store: `email`, an HMAC-SHA-256-hashed OTP code (plaintext never stored, never logged), an attempt counter, expiry, single-use marker. Not a `Registration` — no row here is ever readable by any caller. | `email` |

Three further tables exist as concurrency-safe counters behind the abuse-resistance posture in **§12.5, ADR-010**: `EmailSendBudget` (the atomic per-email OTP send cap), `RegistrationSequence` (the race-safe reference allocator), and `RegistrationLookupAttempt` (the persistent, per-caller-and-reference bound behind the public status lookup — its `ip` column is personal data under GDPR Art. 4(1) / CJEU *Breyer*).

**Four tables of this section hold personal data with no retention or deletion policy** — `Registration.submitterEmail`, `EmailVerification.email`, `EmailSendBudget.email`, `RegistrationLookupAttempt.ip`. This is a recorded, accepted risk (PRD OQ-4), not an oversight: stating it here keeps the public surface honestly sized rather than implied smaller than it is. §3.2 adds two further tables that hold personal data under a stated policy, *retained for compliance*.

### 3.2 ConsentRequest & ConsentDocument (consent requests by email)

Two entities in `backend/prisma/schema.prisma`, behind `ConsentRequestsModule` (§2). **Neither has a relation or foreign key to `Actor`**: `actorId` is a plain string (the `ActorAuditLog.actorId` and `Registration.publishedActorId` shape), so deleting an actor deletes none of its evidence, and each row snapshots `traderId`/`traderName`. No route or job deletes either table, and an answered `ConsentRequest` is never updated again: `src/test/consent-evidence-immutability.spec.ts` pins the set of write sites and that no write can touch an `ACCEPTED` or `DECLINED` row.

| Model | Purpose | Personal data (policy: retained for compliance) |
|---|---|---|
| `ConsentRequest` | One row per attempt to obtain one actor's consent. `status`: `QUEUED · SENDING · SENT · FAILED · ACCEPTED · DECLINED · SUPERSEDED` (*expired* is derived: `SENT` with `expiresAt` in the past, `sentAt + 30 days`). Holds the edition version and SHA-256 hash of the exact text shown, the acting admin, and `tokenHash` (unique SHA-256 of the 32-byte token; the raw token is never stored, logged, audited or returned). | `recipientEmail` (the address at enqueue); on an Accept, `respondentName`, `respondentPosition`, `respondentEmail`, `respondentPhone`; on any answer, Decline included, `respondentIp` and `respondentUserAgent`; `requestedByEmail`; the `traderName` snapshot. |
| `ConsentDocument` | One row per uploaded consent document: `PENDING` (presigned, unconfirmed) → `STORED`; file name, type (`application/pdf`, `image/jpeg`, `image/png`), size, `storageKey`, uploader. Only `STORED` rows are ever listed. The bytes live in the private bucket (`docs/infrastructure.md` §2). | The uploaded document itself (it can name a signatory), `fileName`, `uploadedByEmail`, the `traderName` snapshot. |

**Enum changes.** `ConsentMethod` gains `EMAIL_LINK`, written only by an actor's own Accept and never admin-assertable (§8). `ActorAuditAction` gains `CONSENT_REQUESTED`, `CONSENT_RESPONDED` and `CONSENT_DOCUMENT_UPLOADED`. A `CONSENT_RESPONDED` row is authored by the sentinel `actingSub = 'consent-link'` (`CONSENT_LINK_ACTING_SUB` in `actor-audit.service.ts`, `actingEmail` null, the request id in `changes`) — the first audit identity that is not an admin. `pii-consent.policy.ts` is unchanged: no `Actor` column was added.

## 4. API Surface & Contracts

REST, JSON, versioned under `/api/v1`. List endpoints are paginated (`?page`, `?pageSize`) and filterable. Field projection is role-aware: the full record, on every `admin/actors*` path, is **`Admin`-only** (`AdminActorsController`, class-level `@Roles('Admin')`) — `Staff` gets `403` there, while an anonymous caller gets `401` (QA-3). On actor routes `Staff` reads no differently from `Public`: for `Public`, projection is consent-aware on the detail path only, and a `GRANTED` actor's contact block is included in `GET /api/v1/actors/:id`, and the only other public path that returns it is the token-bearer read `POST /api/v1/consent/view`, which returns it as-if-granted to the holder of that actor's own consent link (§8). *(Corrected 2026-10-05 — the prior wording, "role-aware for `staff`/`admin` (full record, every path)", credited `Staff` with access no route grants; see §8.)*

| Method & path | Auth | Description |
|---|---|---|
| `GET /api/v1/metrics` | Public | Landing-page aggregates. |
| `GET /api/v1/actors` | Public | Paginated/filterable list (`q`, `region`, `crop`, `traderType`, `capacityMin/Max`). Returns the **list set** only — `CONTACT_BLOCK_FIELDS` (`phone`, `email`, `contactPerson`, `position`, `marketLocation`) never appear here, for any actor, under any filter or page size — this is the bulk-exposure boundary the map/dashboard/CSV inherit. |
| `GET /api/v1/actors/:id` | Public | Single actor. For a `GRANTED` actor, returns the full **published set** including the contact block — the only public path **by actor id** that does (the other single-actor read, `POST /consent/view`, is keyed by token — see below). Non-`GRANTED` → `404`, indistinguishable from a missing id. |
| `GET /api/v1/admin/actors` | Admin | Paginated list of all actors (any consent status), full record, with PII and consent filters. |
| `GET /api/v1/admin/actors/:id` | Admin | Single actor, full record, for edit. |
| `POST /api/v1/admin/actors` | Admin | Create (validated DTO). Trader ID is server-assigned (`ActorSequence`), never a client input. A strong duplicate match not named in the request's `confirmedNotDuplicateOf` surfaces as `409` with a `duplicateCandidates` body (`ConflictException`); the `201` response carries any weak matches as `duplicateWarnings`. |
| `PATCH /api/v1/admin/actors/:id` | Admin | Partial update (validated DTO); same consent-provenance gate as create, plus the `EMAIL_LINK` rules of §8. Accepts an optional `expectedUpdatedAt` (ISO instant — the `updatedAt` of the record the form loaded): the actor row is locked first, and a value that differs from the stored `updatedAt` returns `409 { statusCode, error: 'Conflict', message, details: [{ field: 'expectedUpdatedAt', … }] }` with nothing written (D-26). The field is optional on the server; the admin form always sends it. |
| `DELETE /api/v1/admin/actors/:id` | Admin | Permanent delete. |
| `PATCH /api/v1/admin/actors/bulk/consent` | Admin | Set `consentStatus` (`GRANTED`/`DENIED`) for a batch of actors; unlocking to `GRANTED` requires an explicit `acknowledged` flag. |
| `POST /api/v1/admin/actors/bulk/delete` | Admin | Permanently delete a batch of actors (cascading crop links). `POST`, not `DELETE` with a body, for reliable proxy support. |
| `POST /api/v1/admin/actors/import` | Admin | Bulk-import actors from an uploaded `.xlsx` workbook (base64 JSON body; 4 MB decoded / 1,000-data-row caps). **Both modes validate and classify duplicates** against the database and against earlier rows of the same workbook (email/phone = strong, held as `possible-duplicate` unless named in `duplicateConfirmations`; name/GPS = weak, warning only): `mode: 'preview'` does so without writing; `mode: 'commit'` re-validates and re-classifies the same way — every run is a fresh check, so a stale preview confirmation can never pass unchecked — then create-only inserts the surviving rows in 100-row, fault-isolated transactions — the chunk's Trader IDs allocated as one `ActorSequence` range, in a separately-committed transaction immediately before the chunk's transaction opens (a retry on collision re-allocates a fresh range, leaving gaps). *(Corrected 2026-10-05 — the prior wording read as if only `commit` classified duplicates; both modes do, only `commit` writes.)* |
| `GET /api/v1/admin/actors/:id/history` | Admin | Audit history for one actor; works for a deleted actor (no existence check). |
| `GET /api/v1/registrations/consent-policy` | Public | Versioned consent-policy text — one source for the API and the form UI. |
| `POST /api/v1/registrations/verify` | Public | Sends an OTP to the supplied email. **Always `202`, empty body** — deliverable, undeliverable, already-known, and over-cap addresses all get the identical response, so the endpoint cannot be used to test whether an address exists. |
| `POST /api/v1/registrations` | Public | Creates a `Registration` once the OTP is verified. Returns **only** `{ reference }` — no payload echo, no internal `id`. |
| `POST /api/v1/registrations/lookup` | Public | Status by `{ reference, email }` in the request **body**, never a query string (keeps an email address out of request lines, `Referer`, and history). `404` is byte-identical for an absent reference, an email mismatch, and the endpoint's own rate-limit lockout — none is distinguishable from another. |
| `GET /api/v1/admin/registrations` | Admin | Paginated/filterable adjudication queue (`status`, `q`, `region`, `traderType`, `sort`, `page`, `pageSize`); each row carries a `duplicateCandidateCount`, never the candidates themselves. |
| `GET /api/v1/admin/registrations/:id` | Admin | Full registration detail: payload, consent record, duplicate candidates, activity trail. `404` here is a plain not-found, distinguishable from `403` — the public lookup's uniformity requirement (above) stops at the auth boundary; an authenticated Admin is entitled to know whether a registration exists. |
| `POST /api/v1/admin/registrations/:id/approve` | Admin | Single-transaction, compare-and-set approval (`id` + `status = PENDING_REVIEW`; zero rows ⇒ `409` when the row exists, `404` when it does not, DD-22): creates the `Actor`, derives `traderId` (`SR-<year>-<seq>`), writes the literal-picked publishable subset, audits inside the same transaction, links `publishedActorId`. A pre-existing `traderId` also yields `409`, naming the colliding key — never a `500` (ADR-012). |

Request bodies over 32 KB are refused before parsing. Token in the body only, never a path or query string (§8). |

The four public `registrations*` paths are the API's first unauthenticated **write** path (`POST /registrations`) and its first unauthenticated read of anything beyond public directory data (`POST /registrations/lookup`, gated to two scalars). Field projection for them is not role-aware filtering — see §8's structural-containment note. The five `admin/registrations/*` paths are the module's first `Admin`-only, PII-dense surface over that same table — two reads (the queue list, the detail view) and three writes (approve, reject, dismiss-duplicate) — and `approve` is the **only** route in the system that turns a `Registration` into a public `Actor` (§8, ADR-012).

The two public `consent/*` routes are the API's second unauthenticated path that discloses data beyond the public directory (`POST consent/view`) and its first unauthenticated write to an `Actor` (`POST consent/respond`); the thirteen routes of `ConsentRequestsModule` share one module and one derived gate (§2, QA-14). Their authority is a token, not an identity (§8).

## 5. Backend Workflows & Business Rules

- **Role-aware / consent-aware projection:** a single serialization layer enforces PII visibility server-side on every read path (list, detail). The full record is included on every `admin/actors*` path **for `Admin` only** (those routes return `403` to `Staff`, §8); for `Public` — and, on actor routes, `Staff` reads no differently from `Public` — the contact block is withheld everywhere except the single-actor detail read, where it is included only for a `GRANTED` actor, and the token-bearer read `POST consent/view`, which projects it as-if-granted for the holder of that actor's own link (§8). Never relied upon in the client. *(Corrected 2026-10-05, same correction as §4; token-bearer read added by `actors/consent-intake/consent-request-email`.)*
- **Workbook import** (`.xlsx`, base64 JSON body — never CSV, never multipart): parse with `exceljs` → validate each row against the shared intake contract (`common/intake-contract.ts`, the same required set and bounds as admin create/edit) → classify duplicates against existing actors and against earlier rows of the same workbook (email/phone = strong, name/GPS proximity = weak; a strong match is held as `possible-duplicate` unless the admin confirms it in the request) → **create-only**, in per-chunk (100-row) transactions, the chunk's `traderId`s allocated as one `ActorSequence` range (§3), in a separately-committed transaction immediately before the chunk's transaction opens — a collision retry re-allocates a fresh range, leaving gaps. Returns `{ totals: { rows, toCreate, created, possibleDuplicate, failed, warnings }, rows: [{ rowNumber, outcome: 'create' | 'created' | 'possible-duplicate' | 'failed', … }] }`. A bad row, or a chunk whose Trader ID allocation keeps colliding, never corrupts a committed row or chunk.
- **CSV export:** *(Corrected 2026-10-05 — this bullet described the cancelled server-side admin export; see §4 removed-rows note, ATP-53.)* No backend export route exists. The only CSV export is the public `/dashboard` "Download view" button (US-1/AC-6), built client-side in `frontend/lib/dashboard/csv.ts` from the same list projection as the directory — an explicit column allowlist with no contact fields nameable on its input type, so it structurally cannot carry the contact block (`contactPerson`, `position`, `phone`, `email`, `marketLocation`) or `NEVER_PUBLIC_FIELDS`; it does carry consent-disclosed, non-contact fields (`sex`, `otherCrops` — `actors/public-profile-disclosure`).
- **GPS validation:** latitude ∈ [−90,90], longitude ∈ [−180,180]; rows outside range import with GPS nulled + flagged, not plotted.
- **Metrics:** computed via aggregate queries (count distinct regions, count actors with GPS, crops tracked); cacheable.

## 6. Frontend Architecture & State Boundaries

- **Next.js App Router**, **static export** (`output: 'export'`) — no SSR/Next API routes (incompatible with pure S3/CloudFront static hosting). All dynamic data is fetched client-side from the NestJS API.
- **Data fetching:** typed `lib/api` client (fetch wrapper) + React Query (or SWR) for caching/pagination/filter state. Server state stays in the query cache; UI state (filters, modals) in local/URL state. Filters are URL-synced so views are shareable.
- **Auth:** Cognito (Amplify Auth or `oidc-client`) stores JWT; an auth context exposes role; admin routes are client-guarded **and** enforced server-side (client guard is UX only).

Crop-colored markers; filter panel drives query params. When the registry exceeds the ceiling the rail states the shortfall rather than captioning a partial map with the full count (QA-6).
- **Styling:** Tailwind + tokens from `docs/ux-ui/design.md`; shadcn/ui primitives. No hardcoded colors/spacing outside tokens.

## 8. Security & Authorization Model

- **Roles:** `Public` (anonymous; reads public data, plus the token-bearer read and answer below; the contact block appears only on the single-actor detail read for a `GRANTED` actor's own consented fields, and on the token-bearer read below — never on list, geo, dashboard, or export); `Staff` (authenticated: passes `JwtAuthGuard`-only routes such as `GET /api/v1/auth/me` and the one `@Roles('Staff')` route, the probe `GET /api/v1/auth/protected` (Admin ≥ Staff); otherwise reads public, consent-gated actor data the same as `Public`; no actor-write or elevated-read capability today — every actor create/edit/delete/import/PII-read route is `Admin`-only, class-level `@Roles('Admin')` on `AdminActorsController`); `Admin` (full incl. create, edit, delete, import, user mgmt — the only role that reaches any `admin/actors*` or `admin/registrations/*` route). *(Corrected 2026-10-05 — product owner ruling: only `Admin` creates, edits and imports actors; verified against `backend/src/actors/admin-actors.controller.ts` and `backend/src/auth/roles.guard.ts`. The prior wording, "`Staff` (read incl. PII, create/edit)", credited a capability no route grants — `grep -rn "@Roles(" backend/src` turns up exactly one `@Roles('Staff')` site in production code, the auth probe `GET /api/v1/auth/protected`.)*
- **Enforcement:** NestJS `JwtAuthGuard` (validates Cognito JWT signature/claims) + `RolesGuard` (`@Roles('admin')` etc.). PII projection enforced in the serialization layer independent of route guards (defense in depth).
- **Disclosure set (implemented):** `PII_ALLOWLIST` in `src/common/pii-consent.policy.ts` is retained, **empty** — legal has narrowed nothing (yet); it is the one-file re-restriction point if it later does. The boundary is carried instead by two other constants in the same module: `PUBLICLY_DISCLOSED_FIELDS` (`{ phone, email, sex, position, marketLocation, contactPerson, otherCrops }`) — required present, by value, on the single-actor detail read (`GET /api/v1/actors/:id`) for a `GRANTED` actor — and its subset `CONTACT_BLOCK_FIELDS` (`{ phone, email, position, marketLocation, contactPerson }`) — required absent, by key and by value, from the list read (`GET /api/v1/actors`), under every filter/page/page size, so the map/dashboard/CSV structurally cannot carry it. `technicalSupport` sits in `NEVER_PUBLIC_FIELDS` instead — unreviewed staff-authored free text, not an actor PII declaration — alongside `traderId`, `gpsAltitude`, and `gpsAccuracy`, all likewise never public on any path. **Exact GPS is consent-gated:** `gpsLatitude`/`gpsLongitude` are surfaced only for `GRANTED` actors (withheld as `gps: null` for `UNKNOWN`/`DENIED`), on both list and detail, and non-`GRANTED` actors are excluded from every public read by id or list and from `/metrics` counts — the token-bearer read below is the one token-keyed exception. Consent is pinned in the Prisma `WHERE` (not serializer-only) and the boundary — including the list/detail asymmetry — is proven end-to-end over HTTP in `src/test/pii-boundary.spec.ts` (NFR-1, NFR-7).
- **Unapproved-PII boundary (public self-registration).** `Registration.payload` and `Registration.submitterEmail` (§3.1) are PII for an organisation that has not been approved for publication and may never be. **`PII_ALLOWLIST` and `NEVER_PUBLIC_FIELDS` cannot protect this table** — both enumerate `Actor` columns for the `Actor` serializer, and neither one sees a `Registration` row. Protection here is **structural, not filtered**: the public surface (`GET /registrations/consent-policy`, `POST /registrations/verify`, `POST /registrations`, `POST /registrations/lookup`) returns at most two or three scalars (`reference`, `status`, `reviewNote`) and never reads the `payload` column or the internal `id`, before or after adjudication. Proven end-to-end over HTTP by extending `src/test/pii-boundary.spec.ts` to this module's paths — release gate, alongside QA-1's existing coverage (see QA-12, §13).
- **Adjudication authority (public self-registration → public `Actor`).** The five `admin/registrations/*` endpoints (§4) are the **only** path by which a `Registration` becomes a public `Actor`. All five are `Admin`-only: `Staff` → `403`, anonymous → `401` (QA-3). The approve/reject transactions close the double-adjudication race by construction, not by a read-then-check: a conditional update matching `id` **and** `status = PENDING_REVIEW` is the first write, and zero affected rows *is* the refusal (`409`), so there is no window in which a second request can race the first. The reviewer's identity (`reviewedBySub`/`reviewedByEmail`) is resolved server-side from the validated JWT and `ActingAdminResolver` — never client-supplied. The created `Actor` is the only public artifact an approval ever produces; `Registration.payload` and `submitterEmail` stay structurally contained (ADR-010) **before and after** adjudication (ADR-012) — approval publishes a projected subset of the payload, never the row itself.
- **Token-bearer disclosure (consent requests).** `POST consent/view` is the one path on which an anonymous caller reads a **non-`GRANTED`** actor's fields. It is bounded as follows:
  - **Who and what.** The holder of an emailed, open link (status `SENT`, unexpired) reads that one actor: `toPublicDetail` applied to the actor **as if `GRANTED`** — the same function as `GET /actors/:id`, so the page shows exactly what an Accept would publish, exact GPS included — plus the organisation name and the consent text. A test asserts the preview equals the detail read after an accept. **`NEVER_PUBLIC_FIELDS` is never projected**, by key or value, and the respond route echoes no actor or respondent field.
  - **Token.** 32 CSPRNG bytes; only `sha256(token)` is stored; carried only in request bodies (and in the emailed link's URL fragment), never a path or query string, never logged, audited or returned.
  - **Misses.** Every dead end is one `404` with a byte-identical body on both routes; a missing, malformed or wrong-length token is the same miss, never a `400`.
  - **Abuse bounds.** `ConsentThrottleGuard`: 20 requests per 60 s per caller, per route (per container, like ADR-010's limiter — the 256-bit token, not the limiter, is what makes guessing infeasible); `/api/v1/consent` bodies are capped at 32 KB before parsing.
  - **What it is not.** No list, map, dashboard or CSV path carries it, and `CONTACT_BLOCK_FIELDS` stays absent from `GET /actors` (ADR-013). The respondent's evidence (name, position, email, phone, IP, user agent) is readable only on the `Admin`-only `consent-evidence` route.
- **Actor-originated route to `GRANTED`.** `POST consent/respond` with `ACCEPT` is the system's second route to `consentStatus = GRANTED`, and unlike every admin route it comes from the actor and **bypasses the admin acknowledgement**. In one transaction it (0) locks the actor row `FOR UPDATE` as its first statement, (1) closes the request by compare-and-set on the open state (zero rows is the uniform miss, which makes a link answerable once (`view` does not consume it)), (2) sets `consentStatus = GRANTED`, `consentMethod = EMAIL_LINK`, `consentObtainedAt = respondedAt`, `consentReference = <request id>`, and (3) writes one `CONSENT_RESPONDED` audit row authored by `actingSub = 'consent-link'`. `DECLINE` sets `DENIED` only. ADR-NNN records the decision.
- **Admin gate rules for the new method.** (1) *`EMAIL_LINK` is never admin-assertable:* create, bulk consent, import and the import template use `ADMIN_ASSERTABLE_CONSENT_METHODS` (`common/consent-methods.ts`); update accepts the full set but `400`s a **change to** `EMAIL_LINK` and any **transition into `GRANTED`** whose effective method is `EMAIL_LINK`. (2) *Link evidence is frozen:* while an actor is `GRANTED` by `EMAIL_LINK` and stays `GRANTED`, any value change to `consentMethod`, `consentObtainedAt` or `consentReference` is a `400` — correcting it means changing the status first. (3) *A re-grant does not inherit link evidence (D-24):* on a transition into `GRANTED` from a stored `EMAIL_LINK`, the payload must carry its own `consentObtainedAt` (else `400`) and `consentReference` is taken from the payload or set null; bulk unlock applies the same rule. (4) *Stale form (D-26):* `expectedUpdatedAt` mismatch is a `409` (§4). (5) *Supersession:* an admin change to `consentStatus` or `email`, or a delete, supersedes pending requests in the same transaction (§2). (6) *Lock-first ordering:* enqueue, admin update and respond each take the actor row `FOR UPDATE` as their transaction's **first** statement, in the same order, so they cannot deadlock and none reads a snapshot older than the lock — InnoDB's REPEATABLE READ fixes its read view at the first plain read.

**Transport:** HTTPS everywhere (CloudFront + API Gateway). CORS locked to the CloudFront origin.
- **Secrets:** DB credentials and Cognito config from AWS SSM Parameter Store / Secrets Manager — never committed.
- **Input safety:** all writes go through validated DTOs; Prisma parameterizes queries (no raw SQL on user input).

### 12.3 Architecture style

**Modular monolith, deployed serverless.** One NestJS application, internally partitioned into the domain modules of §2, packaged as a *single* Lambda handler. Not microservices: the modules share a datastore and a transaction boundary (the workbook import's per-row validation and per-chunk commit isolation depends on it), and the actor count — 1,000s, not millions — does not justify independent scaling units. Frontend and backend are decoupled at the network boundary only.

**Tactics chosen** (against the scenarios in §13): role-aware **serialization allowlist** + consent pinned in the Prisma `WHERE` (information-hiding, defense in depth); **paginated reads + response compression** (gzip above 1 KB in both bootstraps, `common/compression.config.ts`; a 500-actor page is 140 KB plain and 18 KB gzipped — measured, and the reason the once-planned `/actors/geo` narrow projection was dropped rather than built); **indexed filter columns** (`region`, `traderType`, `consentStatus`, `traderName`); **connection reuse across Lambda invocations** (cold-start and connection-exhaustion mitigation); **stateless compute** (availability via managed redundancy rather than custom failover).

### 12.4 Robust-vs-lite tier decision

**Tier: LITE.** Recorded as **ADR-001** below and cited by `docs/infrastructure.md`.

| Robust-tier machinery | Verdict | Why |
|---|---|---|
| Container platform (ECS/EKS) | **Excluded** | Traffic is low and bursty; Lambda's scale-to-zero fits a public reference registry better than a running cluster. |
| Multi-service decomposition | **Excluded** | Shared transaction boundary + a single team; the coupling cost would exceed the isolation benefit. |
| Event bus / async workers | **Excluded** | The only long-running job is the workbook import, which fits inside a request with per-row reporting. Revisit if import size grows past the Lambda timeout. |
| CQRS / read models | **Excluded** | Read volume is served by indexes and a narrow geo projection. |
| RDS Proxy | **Deferred** | Constrained pool is adequate at current concurrency. Trigger to adopt: sustained concurrent executions approaching the instance's connection ceiling (see OQ-INFRA-4). |
| Multi-AZ / read replica | **Deferred** | Availability target (§13, QA-4) is business-hours best-effort, not an SLA. |

**What LITE does *not* relax:** the PII/consent boundary (§8), input validation, secrets handling, and least-privilege networking. Tier sizing governs *scaling and topology* machinery, never security controls.

"At least", not "≈" — the floor is a floor, a minimum the code pads UP to, never an estimate that could land either side of it.*) — **a cost the product owner accepted explicitly, for now** (`design.md` OQ-11: 2026-09-17, shown the raise from a separate, earlier `3.8 s` statement on 2026-09-16 that remains on record unedited, and told the `4.0 s` figure rests on laptop measurements T-9 may revise — accepted provisionally, not as a settled number) rather than one this design minimizes away; the structural remedy (connecting during Lambda init instead of inside the request) is deferred pending T-9's Lambda-region latency numbers. |
| **ADR-016** | **Cognito's self-service password-reset mail is delivered by a `CustomEmailSender` Lambda trigger, not by Cognito** (`auth/forgot-password-delivery`, `design.md` §3–§6). Cognito keeps the whole reset state machine — it generates the code, expires it, verifies it, and enforces the password policy on the new one (FR-3); **only delivery moved**. The function decrypts the code against a customer-managed symmetric KMS key and publishes it over AMQP to the same OneCGIAR Notification Microservice channel as every other mail in this system (ADR-015), connecting per invocation and caching nothing (DD-3a) so nothing survives a frozen container. **Alternatives rejected:** (a) bring SES out of sandbox — the standing decision is that this system sends only through the microservice; (b) replace Cognito's reset flow with our own — rejected, it would have changed the security shape of a reset for a delivery problem. | Accepted | ⚠️ **The trigger is all-or-nothing per pool**: setting it routes *every* email this pool emits through this function, not only the reset. Unhandled sources raise loudly and visibly rather than failing silently (FR-2), which is deliberate — a silent no-op is how a missing IAM grant survived months in ATP-71. **It adds a new deployable unit inside `10-data-auth`**, a stack that ships only under `DEPLOY_INFRA=true`, so changing the function is slow by construction. ⚠️ **There is no rollback that restores the prior behaviour**: with SES excluded permanently, removing the trigger resumes Cognito's own sending on `COGNITO_DEFAULT`, not on the SES configuration the pool carried before. | **ADR-017** | **Duplicate detection on identity (email/phone strong, name/GPS weak) replaces the Trader-ID natural key as the duplicate guard for team-managed intake** (`actors/consent-intake/intake-required-fields`, `design.md` DD-1…DD-6). Trader ID is no longer a source-data natural key — it is system-assigned (`TM-<year>-<NNNN>`, a per-year `ActorSequence` range allocation, retried on collision up to 3 attempts) for admin-created and imported actors, so it can no longer carry the collision-detection role it held when it came from the source file. Admin create and import now run the same `IntakeDuplicateService` check, reusing `duplicate-detection.service.ts`'s matching functions (not its service or its 5-candidate cap): a **strong** match (shared email or phone) blocks creation until the request names every strong candidate as confirmed — stateless and server-recomputed on every submit, so a stale or reused confirmation can never pass; a **weak** match (name or GPS proximity only) creates the actor with a visible warning. Import classifies the same way against the database and against earlier rows of the same workbook, replacing the `skipped-exists`/`skipped-duplicate-in-file` outcomes with `possible-duplicate`. **Alternatives considered:** (a) keep Trader-ID dedupe — rejected, the ID no longer comes from source data, so a mistyped-id collision can no longer be the detection signal; (b) reuse the registration queue's 5-candidate, match-length-sorted cap for this gate too — rejected, an email-only strong match would lose to five name+GPS weak matches and be created unconfirmed (DD-3); (c) a confirmation token minted at preview time — rejected for stateless server recomputation (DD-4), so a changed email that now matches a different actor is asked about again. | Accepted | **Declared gaps, not deferred fixes:** a **legacy actor with no phone or email** (pre-v4 data) is matched only weakly by name, so a re-imported copy of it is **created**, with a warning naming the match, rather than held as a possible duplicate — accepted under D-3 (all current data is test data), revisited if real legacy data without contact fields is ever imported (`design.md` DD-5 item 2; *added 2026-10-05, validation remediation*). Separately: two concurrent creates sharing an email/phone can both pass the gate (check-then-create; no DB uniqueness on contact fields) — admin-only intake makes this rare, and the audit trail (`ActorAuditLog.duplicateConfirmation`) shows both creates. More than 50 strong candidates behaves differently per surface: an **admin create** with more than 50 strong candidates can never be confirmed (`confirmedNotDuplicateOf` is `ArrayMaxSize(50)`) and the request `409`s outright; an **import row** in the same position instead stays **held** as `possible-duplicate` (the wire cap truncates what is shown, not the gate) — treated as a data-quality signal to clean up, not a product gap. An import preview's **uncompressed** report can exceed Lambda's 6 MB synchronous limit on a file whose rows share one email or phone — measured worst case 3.80 MB with the probe's short trader names, scaling with trader-name length (up to 200 characters) to about **7 MB at 60-character names** (`design.md` §9, added 2026-10-04 during T-5); safety relies on in-Lambda gzip for any client sending `Accept-Encoding`, which every browser does. On MySQL, the collision retry's `P2002` test reads `err.meta.target` as the literal index-name string `Actor_traderId_key` — measured against the local container — not only the field-name array Postgres reports; both forms are accepted, for portability. Candidates and the audit snapshot carry matched-attribute **names** only, never the matched value (NFR-3). |
| **ADR-NNN** *(placeholder; candidate ADR-018 — the number is allocated at apply time on the default branch, never from a spec branch. Checked 2026-10-06: `git log --oneline --all -- docs/trd/trd.md` shows no ref past ADR-017, and no ref carries "ADR-018" in this file.)* | **An actor can reach `GRANTED` by its own answer to an emailed link that can be answered once, and the holder of that link can read what the answer would publish** (`actors/consent-intake/consent-request-email`, `design.md` DD-1…DD-13). Six parts. (1) *Second route to `GRANTED`, actor-originated:* an Accept sets `GRANTED` with `consentMethod = EMAIL_LINK`, a method no admin write can assert, and bypasses the admin acknowledgement (§8). (2) *Token-bearer disclosure:* `POST consent/view` projects a non-`GRANTED` actor through `toPublicDetail` as-if-granted for the link holder only, token in the request body, one uniform `404` for every miss (DD-4, DD-11). (3) *Evidence is FK-less and retained:* `ConsentRequest` and `ConsentDocument` have no relation to `Actor`, snapshot the trader's identity, and are never deleted; answered rows are terminal (§3.2). (4) *Persist, then dispatch:* enqueue persists `QUEUED` rows; the admin's browser drives time-boxed dispatch (7.5 s claim budget, per-row compare-and-set claim, token minted at dispatch, an unknown send outcome becomes `FAILED/stale_claim` and is never auto-resent — DD-1…DD-3). (5) *Lock-first ordering:* enqueue, the admin update's `expectedUpdatedAt` check and respond each lock the actor row `FOR UPDATE` as their transaction's first statement, in the same order (D-25, D-26; InnoDB fixes the read view at the first plain read). (6) *Private S3 document store:* presigned POST with a size and type policy, confirm-and-promote from a self-expiring `incoming/` prefix, 5-minute presigned GET as an attachment, `Retain` (DD-8, DD-12). **Alternatives considered and rejected:** an async worker with its own queue (DD-1 — revisit only if live measurement shows 1,000 sends cannot finish in about 15 minutes); `GET /consent/:token` (puts the token in API Gateway and CloudWatch request lines, DD-4); staying in the `(public)` layout and relying on fragment stripping before analytics mounts (DD-5); presigned PUT, which cannot bound size, and base64 through the API, which meets the 6 MB Lambda limit (DD-8). **Amends** the "only public path that does" sentence in §4's `GET /api/v1/actors/:id` row and the scope of ADR-013's consequence text. **Extends, does not supersede,** ADR-004 and ADR-012: the consent gate still governs every public read by id or list, and registration approval is still the only path from a `Registration` to a public `Actor`. | Accepted | **Possession of the emailed link is the authority for the answer:** anyone who can read that inbox can accept, and the respondent's name, position, email and phone are self-declared and unverified (a respondent email or phone that differs from the actor's leaves the actor's record unchanged). The route bypasses the admin acknowledgement by design, so the trail is the control: one `CONSENT_RESPONDED` audit row authored by `actingSub = 'consent-link'`, the request id in `changes`, and the request row itself holding the text edition and hash, the address used, the respondent, IP and user agent. The limiter is per container (ADR-010's caveat); the 256-bit token is the guess-resistance. Mail inherits ADR-015's guarantee — a confirmed publish means *enqueued*, not *delivered*. Personal data now sits in two more tables, *retained for compliance* (§3.2), and the bucket's `Retain` means a stack teardown leaves compliance evidence behind for manual cleanup (`docs/infrastructure.md` §2). The e2e harness mocks Prisma, so InnoDB lock behaviour is corroborated only by throwaway probes recorded in the spec's `execution.md`, not by a committed test. `20-backend` deploys on every merge to `main`, so the bucket is created by the first merge and the deploy role must be able to create it (`docs/infrastructure.md` §2). |
